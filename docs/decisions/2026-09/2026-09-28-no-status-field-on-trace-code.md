# ADR：TRACE_CODE 不设 status 字段，在架由单据集合推导

- 日期：2026-09-28
- 状态：已拍板
- 关联：prototypes/shared/diagrams/13-box-instance.html（箱码全链路实例）

## 结论

库房在架**不在追溯码上打 status**，由单据集合推导：

```
库房在架 = 该库房已审核入库单的码集合 − 已审核出库单的码集合
在途     = 已出库、药房未确认入库的部分
```

TRACE_CODE 从不删行；同一条码同时出现在入库单与出库单的 DOC_CODE（「码随单转」）。

## 第一性原理

**库存不是事实，是过去所有事件的函数。** status 字段不产生新信息，只是缓存。缓存三问：

| 缓存三问 | 纯推导（本设计） | 加 status 字段 |
|---|---|---|
| 查询成本 | 集合差，毫秒级（在架 10⁵ 码规模） | O(1) 点查，但省的不是瓶颈 |
| 一致性 | 天然一致——没有第二份数据可错 | 审核双写（单据+码状态），写一半崩 = 静默错账 |
| 可重建 | 无需重建 | 能重建，但得先发现它错了 |

银行余额类比：流水是事实，余额是缓存；银行为缓存养着整套对账体系。不要缓存，就永远不用跟自己对账（与 HIS/监管平台的跨系统对账照做）。

## 为什么在本场景成立

1. **监管审计优先**：药品追溯码国家强制，监管问「某时点码在哪」——推导天然回答任意时点；append-only 无「改状态」后门，防篡改面最小。
2. **规模够不着瓶颈**：院区在架 10⁴–10⁵ 码、年流水 10⁶–10⁷，集合差有索引毫秒级。
3. **幂等白捡**：重复审核/冲正 = 多一条单据记录，推导自动正确；status 模型每个操作都要补偿逻辑。

## 边界与代价（认账）

- **分界按查询模式划**：`location` / `split` / `splitQty` 是冗余（单码高频点查）；在架/在途保持推导（聚合集合运算）。
- 代价 ①：推导规则必须收敛成**唯一函数**，禁止第二处实现，防报表漏算某类单据导致数字分叉且无报警。
- 代价 ②：新增单据类型必须登记方向（入/出/中性）→ docType 方向配置表。
- 代价 ③：出库审核前现查该码最新动向防重复出库；生产化用唯一约束/串行审核事务兜底。

## 何时加缓存（触发信号）

跨院区实时看板秒开 / 流水破千万行 / 外部系统高频查库存 / 盘点锁快照。届时加**物化视图 + 对账 job**：流水为王，缓存为奴——谁都能删缓存，没人能改流水。
