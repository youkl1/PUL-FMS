# PUL-FMS 业务流程图与 UML 图设计方案

> 日期：2026-09-22
> 用途：开发交接 / 技术评审
> 产出：Mermaid 源文件（.mmd，可 git diff）+ HTML 浏览壳（index.html）

---

## 1. 背景与目标

PUL-FMS（药品现场精细化管理系统）已交付 27 页原型（登录骨架、字典、采购、库房 4 大模块），但系统的核心机制——**「码⇄药⇄单位」转换层**——目前只以代码形式存在（`drug-data.js` 的 conv 引擎），没有任何图示。开发交接需要一套图纸把全业务链路讲清楚。

### 设计原则（已与用户拍板）

1. **场景驱动**：每张流程图回答「谁、在什么条件下、做什么、药品此刻以什么形态存在」——映射真实业务，不映射原型页面完成度；以第一性原理从用户角度分析场景需求
2. **转换层是心脏**：码⇄药⇄单位的表存储结构和节点转换单独两张图讲透
3. **灵活兜底**：凡是自动解析可能失败的节点，必须画出人工后台维护入口；药房「入槽」与「不入槽直接发」是两条并列合法路径
4. **后期段不回避**：处方→码映射等未设计环节，以「待决方案分支」画出供评审讨论，图上不替评审拍板（推荐倾向可标注）

## 3. 核心机制事实依据（已从代码核实）

```
20 位追溯码 = 7 位标识码(产品资源码) + 9 位序列号 + 4 位校验位
parseCode(): slice(0,7) 查 IDCODES 子表 → 命中=drugCode+level+packUnit；未命中=null→异常码
conv(): units 换算链 [{u:'箱',eq:60},{u:'瓶',eq:1}]，eq=折合链尾单位数，链尾=库存基本单位
minUnit {u:'片',per:7} = 拆零最小制剂单位
库存双口径：存储按「码」（逐码带批次/效期/库位）；申请/统计按「药」（基本单位）→ 双层表达
```

出处：`scripts/drug-data.js`、`scripts/purchase-data.js:122-127`、`scripts/wh-pick.js`、`scripts/wh-data.js`

## 4. 处方→码映射：3 个待决方案（图 4 / 图 7 挂出）

| 方案 | 机制 | 优点 | 风险 |
|------|------|------|------|
| a. 开单即锁码 | 开方时按 FEFO 预分配追溯码，库存锁定 | 追溯最严 | 退单/改单要释放锁，复杂 |
| b. 锁药品级库存，调剂时分配码 | 处方只锁数量，调剂出库时才绑定具体码 | 灵活，与「不入槽也能出」兼容 | 「库存有药却扫不出码」边界需处理 |
| c. 完全后绑定 | 出库扫码时才扣账 | 最简单 | 库存超卖风险 |

用户倾向「灵活为主」，图上并列三方案，推荐标注但不拍板。
