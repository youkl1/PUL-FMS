## 一、第一性原理与老系统证据

### 1.1 物理事实与单据

库房→药房领用只有三个物理事件，单据是凭证：

| 事件 | 凭证 | 必然性 |
|------|------|--------|
| E1 要药 | 领用单（reqPool：药房申请 / 库房制单） | 可选（紧急/主动补货时无） |
| E2 药离开库房 | 领用出库单（pickDocs），扣账时点=审核出库 | 必有 |
| E3 药房收货 | 入库闭环（pickDocs.status=药房已入库） | 必有 |

**备货是 E2 之前的拣货作业环节，不是独立单据**——「备货单」= 待备货领用单 + 备货中出库单草稿的工作队列视图。

### 1.2 老系统截图还原（2026-10-01 用户提供，库房系统）

一张"领用单"四态状态机 + 三个来源：

| 环节 | 老系统页面 | 干什么 | 状态推进 |
|------|-----------|--------|----------|
| 制单 | 缺药领用单 | 选出库库房+领用药房+上架货位 → 药品选择器（**名称/拼音码模糊搜索 + 药房存量/零头 + 库房存量/零头四列** + 按货位过滤：拆零货位出柜号/层号/取药槽清单 11 条，普通货位全量 1243 条）→ 填单据数量 | 待提交 →提交→ 待备货 |
| 备药 | 缺药备货 | 编辑明细填**实物数量/实物零头**（不扫码）→ 提交出库 | 待备货 → 待出库 |
| 出库 | 领用出库 | 待出库单扫码逐码过账 | 待出库 → 完成 |
| 快捷 | 领用扫码 | 直接扫码生成待出库单（来源=领用扫码） | 跳过制单+备货 |

单据来源三值：缺药领用 / 领用扫码 / 采购入库。

### 1.3 备货语义定论（本轮拍板）

老系统备货 = **数量级确认**（实物数，不扫码），扫码在领用出库——拣货/复核两段制，是码粒度弱时代的形态。
**本系统采一体制：备货 = 扫码拣货，数量由码折合、与申请数实时对差**——追溯码系统里数量必须与码一致，两段制只会引入"实物数≠码数"的差异负担。不恢复数量确认独立环节。

## 二、目标状态机（统一口径）

```
领用单 reqPool：   待提交(仅库房制单) → 待备货 → 备货中 → 已完成
出库单 pickDocs：  备货中(草稿) → 已出库(在途·扣账) → 药房已入库(闭环)
```

- 领用单 ↔ 出库单 1:1（沿用 docOfReq）
- req.status 为**存储值**：wh-pick 建草稿时回写 `备货中`，草稿作废回写 `待备货`，审核回写 `已完成`；`待提交` 仅库房制单路径产生
- reqPool 加 `source` 字段：`药房申请`（ph-req，默认）/ `库房制单`（wh-pick-out 新增）
- 「待提交」不进备货队列（wh-pick 不显示），只在 wh-pick-out 制单管理

## 三、入口同构：所有备货 = 在一张备货中出库单上扫码

| 入口 | 动作 | 关联领用单 |
|------|------|-----------|
| 备货单页：待备货行点「备货」 | 建/复用草稿 pickDoc（回写 req 备货中），进工作台 | ✓ |
| 出库单页「+ 新增单据」 | 完整制单（§六）→ 待提交草稿 → 提交后 → 待备货 | ✓（制单） |
| 备货单页「直接扫码出库」 | 弹窗选领用药房+备注 → 建空草稿 → 进工作台，扫完即审 | ✗ |

- 「⚡一步式领用（跳过备货）」更名「直接扫码出库」
- 与老系统差异说明：老系统领用扫码扫完落「待出库」（扫/过账分离）；本系统扫完即审（同人同场景），不引入扫/审分离（Non-goal）

## 四、双页分工

### 4.1 领用备货单 wh-pick = 工作台

- 列表 = 领用单链（待备货/备货中/已完成）+ 无申请草稿行；状态列四档：**待备货 / 备货中 / 已出库·在途 / 药房已入库**，筛选同步；不显示待提交
- 行操作：待备货→「备货」；备货中→「继续备货」；已出库→「确认药房入库」（演示闭环）；已入库→「闭环」
- 工作台模式：`doc.codes` 为唯一事实源（废弃 `picked={}` 内存态），扫码/移除/清空实时写回 + save——**刷新不丢、换班可续**
- 深链 `?billNo=X`：备货中→工作台；已出库/已入库→只读
- 审核出库：草稿推进已出库（不再 unshift 新单），写 auditTime/operator/expectLoc，回写 req 已完成

### 4.2 领用出库单 wh-pick-out = 台账 + 制单

- 列表 = 全部 pickDocs（含备货中草稿）+ reqPool 中 `source=库房制单 且 status=待提交` 的制单草稿行（操作：编辑/提交/删除）
- 状态列去 stText 映射，直接显示备货中/已出库/药房已入库；筛选同步
- 备货中行操作：「继续备货 →」跳 wh-pick?billNo=（原「✓审核出库」改名，审核只在工作台）+「✗ 作废」
- **作废放宽**：备货中草稿有无码均可作废（未扣账无库存副作用），confirm 提示「码未扣账，作废即释放」；有关联领用单回写待备货；删除现有码拦截
- 「+ 新增单据」升级为完整制单弹窗（§六）

### 4.3 不动的页面

出库明细查询、入库明细查询、领用入库、药房库存——均只见过账单据，天然兼容。

## 五、共享药品选择器组件（新组件，解决 N1）

新文件 `scripts/drug-picker.js`（原型级，沿用 purchase-shared.js 的弹窗模式）：

- **搜索**：药品名称 / 药品编码 / 生产厂家 模糊匹配（**字典无拼音码字段**，本期不支持拼音搜索，见开放问题）
- **列表列**（对齐老系统）：药品名称 / 规格 / 剂型 / **药房存量 / 药房零头 / 库房存量 / 库房零头** / 生产厂家 / 批准文号 / 药品编码
  - 库房存量 = `stockAll` 按 drugCode 聚合（码数×折合）；零头 = 拆零码 splitQty 累计
  - 药房存量 = `pharmacyStock(wh, 药房)` 同口径聚合
- **货位过滤**：下拉选该药房货位 → 只显示该货位 `phLoc` 在架的药品（近似老系统拆零货位出清单；取药柜槽号列无绑定数据，Non-goal）
- **交互**：勾选 → 确认选择 → 进入已选清单（填数量，基本单位）→ 保存
- **复用点**：ph-req 申请编辑（替换现有 per-row `<select>` 全量下拉）、wh-pick-out 库房制单

## 六、库房主动制单（缺药领用单，解决 N3）

- 入口：wh-pick-out「+ 新增单据」（不新增菜单页）
- 弹窗内容：领用药房（必选）+ 上架货位过滤（选填，作用于选择器）+ 药品选择器 + 数量 + 备注
- 保存 = reqPool 加 `{reqNo(LY 前缀), source:'库房制单', status:'待提交', applicant:当前库房用户, pharmacy, warehouse:当前库房, items[]}`
- 待提交行操作：编辑（重开制单弹窗）/ 提交（status→待备货，进入 wh-pick 备货队列）/ 删除
- 与药房申请差异：无「待提交」（9-30 拍板维持：药房提交即待备货）

## 七、联动与防重

| 场景 | 规则 |
|------|------|
| ph-req 申请侧 | 备货中锁定（文案「库房备货中」）；待备货可编辑/撤销；已完成只读；编辑器换共享选择器 |
| quick-scan 快捷扫码 | 选领用单时已有备货中草稿 → 拦截「该申请正在备货中，请到领用备货单继续」；无草稿维持现状（审核才建单直接已出库）。一屏连续作业无续作场景，不改草稿制 |
| ledger-data.js L52 | pickDocs 循环加 `if (!W.pickPosted(d)) return;` |
| 审核时再校验 | 草稿可能放置期间码被其他出库/损耗出掉：审核对照 stockMap 重验，失效码列出，要求移除后再审 |

## 八、数据与种子

- pickDoc 字段不变；备货中草稿 auditTime 为空
- reqPool 加 `source`（migrate 兜底 `药房申请`）
- wh-data.js seed：+1 条备货中草稿（含 2 个在架码，关联 1 条领用单→status 备货中）；+1 条库房制单待提交草稿
- migrate 其余不动（无状态假设）

## 九、边界与异常清单

| 边界 | 处理 |
|------|------|
| 空草稿审核 | 审核按钮 disabled（现状） |
| 超申请数扫码 | warn 不拦截（现状） |
| 非在架/重复/非本单药品码 | 拦截（现状） |
| 重复点「备货」 | 复用已有草稿不重复建单 |
| 作废有码草稿 | 允许，confirm；有关联领用单回写待备货 |
| 草稿码被其他单据出掉 | 审核时重验在架，失效码列出拦截 |
| 无申请直接出库 | 不带上架货位（expectLoc 空） |
| 待提交制单 | 不进备货队列/不进流水；可编辑/提交/删除 |
| 选择器零存量药品 | 照常显示（存量 0 标灰），允许申请（缺药场景正是要申请） |
| 库房冻结 | assertUnfrozen 拦截（现状） |

## 十一、验证方式

1. `_t-invariants.node.js` 既有断言（备货中不扣账）继续通过
2. `_t-wh-pick.html` 自动交互测试更新后跑通（headless 截图）
3. 手动走查六条路径：申请→备货→审核→入库闭环；库房制单→待提交→提交→备货；直接扫码出库；作废有码草稿→申请恢复待备货；快捷扫码选已备货申请被拦截；选择器搜索+存量列+货位过滤
4. 流水台账确认草稿/待提交不出现

## 十二、Non-Goals

- 不恢复"数量确认"两段制备货（一体制已拍板）
- 不引入领用扫码的扫/过账分离
- 不加拼音码字段（字典导入带拼音时再补，选择器搜索维度预留）
- 不做取药柜槽号↔货位绑定（Round I 决策④后期再议；货位过滤按 phLoc 在架近似）
- 不做真并发锁；不改库存推导/在途口径/药房入库核对
- 不补写 pickOut PRD（本稿可作为其输入）

## 十三、开放问题

3. 库房制单是否需挂在「缺货查询/预警」驱动上（老系统存量管理组）？本期仅手工制单入口
