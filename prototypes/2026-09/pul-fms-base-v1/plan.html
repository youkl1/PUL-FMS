架构概览
定位：PUL-FMS 后台原型——登录上下文 + 组织/字典底座，采购→库房→药房→发药（方案 b）→病区签收可点通；台账只读派生，盘点账实对照后过账。
架构：多页 location.href 跳转、无构建步骤；UI 分层 = pi 原型壳（prototype-intro.css）+ Tabler 1.5.1 本地化（../../shared/tabler/，方案 B）+ 自有后台壳（app-shell.js 侧边栏/顶栏）+ 页面 CSS/JS；登录态经 store.js（sessionStorage）跨页共享。
权限模型：沿用若依（RuoYi）成熟方案 —— RBAC 角色-菜单树 + 数据权限 5 档 DataScope（全部 / 自定义 / 本院区 / 本院区及以下 / 仅本人），数据范围挂在角色上，用户通过多选角色继承；与研发框架 yudao 的 system_role.data_scope 原生能力一致。登录：先验账号，单一节点角色直接进工作台，多节点角色才选院区 / 模式 / 库房（候选集由角色数据范围算出），顶栏常驻上下文并可「部门切换」。

架构约束
  • 路由方式：多页 location.href 跳转 + URL 参数（dict-types → dict-items?type=CODE），不用 hash 路由、无前端框架
  • UI 分层：Tabler 1.5.1 本地化（prototypes/shared/tabler/）负责业务组件（卡片/表格/按钮/表单/徽标）；app-shell.js 自有壳负责侧边栏+顶栏（Tabler 的 fixed 侧边栏无法嵌入预览容器，故壳自研、视觉对齐 Tabler）
  • 权限模型（2026-09-22 定稿，对齐研发框架 yudao）：功能权限与数据权限都挂角色 —— 菜单/按钮树 + 若依 DataScope 五档（system_role.data_scope），用户多选角色继承，登录候选上下文由角色范围并集算出；行数据 = 登录所选库房/药房自动隔离 → 再按本人隔离。超级用户不指定院区、不可删、不参与业务
  • 多院区单实例（2026-09-21 拍板，推翻旧决策#4 独立部署）：一套实例多院区，超级用户登录时选院区，非超管自动进入唯一所属院区
  • 登录上下文：先验账号密码 → 超管选院区/非超管自动进入 → 既属库房又属药房的用户先选「库房管理/药房管理」→ 选具体库房/药房；顶栏常驻上下文并支持「部门切换」
  • 状态共享：登录态存 store.js（sessionStorage）；未登录直达任何页自动注入演示账号并标「演示模式」
  • 数据约定：组织/角色/用户在 data.js；药品字典 drug-data.js；采购 purchase-data.js；库房/药房单据 wh-data.js；发药 rx-data.js；盘点 inv-data.js。库存数量 = 码 count 派生。页内编辑为内存态
  • 无构建步骤：从 prototypes 根目录起任意静态服务即可运行，无 npm 依赖
已知限制（3 项）
  • 编辑不持久：用户/角色/院区/字典页内的新增、编辑、启停、禁用为内存态，刷新页面即还原（演示用途，不接后端）
  • 菜单未按角色过滤：目前所有角色看到的左侧菜单相同，仅工作台「数据范围卡」与角色页体现差异；「换账号菜单真实变化」待下一阶段连同业务模块一起做
  • 权限勾选不落库：角色弹窗里的菜单树/数据范围勾选，保存仅更新本页预览 + toast，不会真正改变其他账号的可见菜单与数据
